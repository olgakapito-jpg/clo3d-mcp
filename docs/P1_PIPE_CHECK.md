# P1: короткая проверка Named Pipe в настоящем CLO

Статус: **P1 принят**. Локальные Windows-тесты и реальный цикл pipe/API/STOP
пройдены; пользователь подтвердил отзывчивость UI с закрытым Script Editor.
P0 принят, повторять его минутный или длинный прогон не нужно.
Это только транспортная диагностика: MCP endpoint и очередь пока отсутствуют.

## Полученный реальный результат

Пользователь прислал поколение 1: `FINISHED`, затем неизменный `STOP_STATUS`.
22 ticks, owner/callback thread совпадают, connections=2, disconnects=1,
handshakes=2, jobs=4, api_calls=2, pattern_count=0. Завершение: state=stopped,
stop_reason=peer_stop, child_exit_code=0, оба cleanup_pending=False, error=None,
reentrant_ticks=0. Нулевой счётчик допустим для пустой сцены. Реальный обмен,
переподключение, API-чтение и завершение подтверждены этим выводом. Отдельным
ответом пользователь явно подтвердил закрытый Script Editor и отзывчивый UI.
Gate P1 закрыт для проверенной среды CLO; повторный прогон не требуется.

## Что запускается

`diagnostics/clo3d_mcp_pipe_probe.py` использует проверенный P0 Win32 timer adapter,
но не запускает P0 и не импортирует legacy listener. Внешний Python создаёт
локальный Named Pipe с DACL текущего пользователя и запретом удалённых клиентов.
Случайный секрет передаётся через окружение, проверяются HMAC и реальные PID
обоих концов. Он не записывается в исходники, аргументы команды или логи.

Диагностика выполняет два раунда:
1. Handshake, `ping`, одно чтение `pattern_api.GetPatternCount()`.
2. Намеренный разрыв pipe, переподключение, новый handshake, ещё `ping` и чтение.
3. STOP/ответ STOP, завершение дочернего процесса, отмена pending I/O и таймера.

Сцена не изменяется. Нулевое число деталей допустимо. Команды после разрыва
не переотправляются: второй раунд имеет новые job_id. Незавершённый кадр
считается ошибкой, а не основанием повторить команду.

## Запуск в CLO

- В том же проверенном CLO откройте `diagnostics/clo3d_mcp_pipe_probe.py`
  в Script Editor и выполните один раз. Внешняя `.venv` уже подготовлена;
  устанавливать что-либо во встроенный Python не нужно.
- Если CLO сообщает, что нет `__file__`, укажите абсолютный каталог проекта
  в `ROOT` в начале launcher. Произвольный текущий каталог не используется.
- После `STARTED (not yet connected)` закройте Script Editor и несколько секунд
  поработайте с UI. Затем откройте вывод и проверьте итог `FINISHED`.
- Нормально весь цикл занимает несколько секунд, обычно меньше 15 секунд.
  Внешний процесс ограничен 75 секундами, runtime — 90 секундами активного
  обслуживания callback. Это защитные пределы, не требуемая длительность теста.
  Если callbacks не обслуживаются или CLO API завис, wall-clock срок завершения
  в UI не гарантируется; внешний процесс имеет собственный срок.

## Ожидаемый итог

В строке `[CLO P1] FINISHED`:

```text
state: stopped
connections: 2
disconnects: 1
handshakes: 2
jobs: 4
api_calls: 2
pattern_count: <число деталей сцены>
stop_reason: peer_stop
pipe_cleanup_pending: False
timer_cleanup_pending: False
child_exit_code: 0
error: None
```

`owner_thread` и `callback_thread` должны совпадать. `STARTED` сам по себе
не подтверждает ни handshake, ни работоспособность API. Четыре jobs — это
два ping и два чтения; не четыре вызова CLO API.

Повторный запуск launcher **во время активного цикла** выдаёт `ALREADY_STARTED`
и не создаёт второй процесс. После FINISHED новый запуск создаёт новое поколение;
для P1 удерживается максимум 16 поколений callback до закрытия CLO.

## Остановка и отчёт

В любой момент выполните `diagnostics/clo3d_mcp_pipe_probe_stop.py` в CLO.
Он останавливает только текущий P1 и его дочерний процесс, не CLO и не чужие
процессы. При pending I/O очистка продолжается следующими callback без ожидания
в UI. Поэтому первый STOP_STATUS может ещё показывать `stopping`.

После обычного FINISHED выполните stop-скрипт для итогового отчёта, затем
ещё раз через пару секунд: jobs/api_calls не должны расти, причина `peer_stop`
сохраняется. Повторный stop не возобновляет транспорт.

Критерии провала: зависание UI, несовпадение thread IDs, `state=failed`,
`error` не None, отсутствие FINISHED или остающаяся незавершённая очистка.
При провале выполните stop-скрипт и пришлите последние строки `[CLO P1]`;
не запускайте несколько новых попыток поверх незавершённой.

Для приёмки достаточно прислать FINISHED/STOP_STATUS и подтвердить отзывчивость
UI с закрытым редактором. Не нужны приватные сцены, токены или окружение процесса.

## Границы проверки и реализация запуска

- Кадры: uint32 LE + JSON UTF-8, максимум 1 MiB; capabilities строго ограничены
  `ping` и `get_pattern_count`. Один CLO job, не более одного входящего сообщения
  сервера на обмен, один read/write chunk на poll. CLO callback не ждёт pipe.
- `.venv/Scripts/python.exe` в Windows — redirector. Чтобы PID `Popen` совпадал
  с владельцем pipe, читается `home` из `.venv/pyvenv.cfg`, запускается именно
  этот base CPython с `__PYVENV_LAUNCHER__`, указывающим на явный venv Python.
  Отдельный реальный тест проверяет PID, `sys.executable` и `sys.prefix`.
  При недоступном base нет fallback на PATH/встроенный Python.
- Единственные чтения конфигурации — исходники и pyvenv.cfg; новые request,
  response, discovery, heartbeat или queue файлы не создаются. Bytecode-запись
  внешнего процесса выключена; обычные Python cache-файлы не являются IPC.
- Эта диагностика ещё не реализует FIFO, HTTP, наблюдение за handle CLO до его
  смерти, долговременный сервис или возобновление неизвестного результата.
  При ручном stop выполняющийся синхронный CLO API не обещает прерываться.
- Автотесты с fake API/таймером не являются доказательством работы внутри CLO.
  Реальная приёмка выше обязательна до объявления P1 завершённым.
