# P2: ограниченная внешняя очередь

Статус: **P2 принят**. Локальные тесты и реальный диагностический цикл пройдены;
пользователь явно подтвердил отзывчивость UI с закрытым Script Editor.
P0/P1 уже приняты и повторять их не нужно. HTTP/MCP endpoint ещё не запускается.

## Полученный реальный результат

Пользователь прислал FINISHED и неизменный STOP_STATUS поколения 1: 21 ticks,
owner_thread=callback_thread=10888, connections=1, disconnects=0, handshakes=1,
jobs=5, api_calls=2, pattern_count=0, reentrant_ticks=0. Завершение: stopped,
peer_stop, child_exit_code=0, оба cleanup_pending=False, error=None.
Успешный код внешней диагностики подтверждает её проверки FIFO/cancel/deadlines/
late result/queue_full. Отдельным ответом пользователь явно подтвердил закрытый
Script Editor и отзывчивый UI. Gate P2 закрыт для проверенной среды CLO;
повторный прогон не требуется. HTTP и долговременный lifecycle проверяются в P3.

## Семантика

- Очередь существует только во внешнем Python: 32 ожидающих задания плюс одно
  отправленное/выполняемое. Даже read-only команды последовательны.
- Срок в очереди отсчитывается от submit, срок ответа — от dispatch. Deadline
  означает `outcome_unknown`, а не остановку CLO API; слот остаётся занят.
- RESULT/ERROR сопоставляется по session_id/job_id. Следующее задание требует
  подтверждённого результата и READY, не одного ACK или READY.
- Отмена `call()` до dispatch удаляет задание. После dispatch отменяется только
  ожидание клиента. `wait()` наблюдает существующий ID и ничего не отправляет.
- Поздний результат обновляет lookup, но уже получивший timeout клиент не
  превращается задним числом в успешный. Повторной отправки нет.
- Разрыв с unresolved dispatch переводит сеанс в карантин: queued получают
  executor_unavailable, active — outcome_unknown. Даже новый handshake/READY
  не снимает карантин. Требуется явный новый сеанс, без переноса старых jobs.
  Если RESULT был принят до разрыва, он уже доказывает завершение.
- Сервер сам назначает возрастающие IDs; произвольный ID для повторного submit
  не принимается. Завершённые результаты: до 128, waiters: до 128. После eviction
  lookup даёт job_not_found и не повторяет команду; память между процессами
  не сохраняется. exactly-once при падении не обещается.
- `running` возможен только при явном execution receipt через started().
  Текущий wire-протокол такого сообщения не имеет, поэтому до результата
  состояние остаётся `dispatched`, без выдуманного подтверждения старта API.
- status доступен, пока CLO занят. HTTP/его client cancellation будут проверяться
  отдельно в P3; сейчас проверена отмена обычных async callers.

## Короткий запуск в CLO

1. Используйте свежий запуск CLO: ранее импортированный P1 runtime остаётся
   в памяти Python, а код launcher получил выбор P2-профиля. Горячая перезагрузка
   объектов native callback намеренно не выполняется. P0/P1 повторять не нужно.
2. Откройте и выполните `plugin/clo3d_mcp_queue_probe.py`. Если CLO не предоставляет
   `__file__`, задайте `ROOT` в начале этого скрипта — абсолютный каталог проекта.
3. После `[CLO P2] STARTED` закройте Script Editor и поработайте с UI несколько
   секунд. Нормальная длительность — менее 15 секунд, не стресс-тест.
4. Проверьте `[CLO P2] FINISHED`. Для остановки/отчёта выполните
   `plugin/clo3d_mcp_queue_probe_stop.py`.

Ожидаемый итог:

```text
state: stopped
connections: 1
disconnects: 0
handshakes: 1
jobs: 5
api_calls: 2
pattern_count: <число деталей, включая допустимый 0>
stop_reason: peer_stop
pipe_cleanup_pending: False
timer_cleanup_pending: False
child_exit_code: 0
error: None
```

owner_thread и callback_thread должны совпасть. Повторный stop сохраняет
счётчики. Повторный запуск активного P2 не создаёт второй процесс, а запуск
другого P1/P2 поверх активного блокируется. Каждое семейство удерживает не более
16 поколений callback. Сцена не изменяется, legacy listener не импортируется.

## Что означает успешный child_exit_code=0

Внешняя диагностика проверяет до отправки STOP:
- Шесть конкурентных callers: ping, count, count, ping, count, ping.
- Третий count отменяется ДО dispatch: в CLO не попадает.
- Очередь заполняется до 32, лишний submit получает queue_full; служебные jobs
  затем отменяются ДО dispatch, не вызывая API.
- Отдельное queued чтение получает queue_timeout, не отправляясь в CLO.
- Четвёртое задание (ping) получает искусственно короткий dispatch deadline
  во внешнем процессе. Слот остаётся занят, запрос всё равно отправляется ровно
  один раз, принимается поздний результат, только затем dispatch следующего.
- Внешний процесс сверяет FIFO, результаты callers и поздний lookup; лишь после
  успеха отправляет STOP. Ошибка проверки даёт ненулевой exit code, не успех.

Инъекция тайм-аута выполняется **снаружи**, не задержкой/сном в UI и не изменением
сцены. Пять выполненных jobs — три ping и два count. Неизвестный исход при разрыве
проверен отдельно детерминированными тестами; этот короткий CLO-тест намеренно
не обрывает выполняющийся API и не доказывает безопасность долгих CLO-вызовов.

Внешняя диагностика ограничена 60 секундами плюс очистка; runtime — 90 секундами
обслуживаемых callback. Stop не обещает прерывание синхронного CLO API.
При ошибке/отсутствии FINISHED/зависании UI выполните stop, пришлите последние
строки `[CLO P2]`, не запускайте новые поколения поверх незавершённой очистки.

Для приёмки пришлите FINISHED/STOP_STATUS и подтвердите отзывчивость UI с закрытым
Script Editor. После неё следующий этап — минимальный официальный FastMCP HTTP,
для которого ещё нужно уточнить MCP-клиент и согласовать loopback-порт 8765.
