# P0: проверка callback в реальном CLO

## Статус и границы

Независимый probe проверен пользователем в CLO: callbacks/API работают с закрытым
редактором, UI отзывчив, десять коротких циклов и ручная остановка успешны.
Длинный прогон дал 120 API-чтений (не менее примерно 597 секунд; точное время
старый отчёт не сохранял). По просьбе пользователя оставшуюся проверку автостопа
проводим за **60 секунд**, без повторения длительного прогона.
**P0 принят для перехода к P1** по совокупности реальных испытаний и согласованному
уточнению проверки. В новом сеансе CLO получено: `elapsed_seconds=60.016`,
`stop_reason=one_minute_limit`, 240 callbacks, 12 API-чтений, `pattern_count=5`,
одинаковый owner/callback thread, `state=stopped`,
`timer_cleanup_pending=False`, `error=None`, без reentrancy.
Это подтверждает минутный автостоп, но не доказывает полные 600 секунд длинного
прогона. Повторять уже выполненные проверки не требуется.
Probe не запускает MCP, не использует Named Pipe и не импортирует старый listener.
Не создаёт файлов команд/ответов/heartbeat и не изменяет сцену: единственный
вызов CLO API — `pattern_api.GetPatternCount()`.

Win32 `SetTimer` требует обработки сообщений на регистрирующем потоке.
Успешный `SetTimer`, внешний тест Windows и mock-тесты не доказывают, что CLO
будет обслуживать callback после возврата Script Editor.

## Первый запуск

1. Использовать отдельный тестовый сеанс CLO без запущенного старого listener.
   Если его состояние неизвестно, сначала штатно закрыть и открыть CLO.
2. В Script Editor открыть и выполнить `plugin/clo3d_mcp_probe.py` из этого проекта.
   Это один самостоятельный файл; внешняя `.venv` ему не нужна.
3. Сохранить вывод `Python=...`, `ctypes=...`, `module=...` и `ARMED ...`.
   После `ARMED` скрипт должен вернуть управление, без цикла ожидания.
4. Примерно через две секунды при свободном UI ожидается `FIRST_API ...`:
   `state: running`, одинаковые `owner_thread` и `callback_thread`,
   `api_calls: 1`, `pattern_count` — число деталей текущего проекта.
5. Закрыть Script Editor и работать с интерфейсом CLO. Через 30–60 секунд открыть
   его и повторно выполнить **тот же** `clo3d_mcp_probe.py`: ожидается
   `ALREADY_RUNNING`, та же `generation`, увеличившиеся `ticks` и `api_calls`.
   Повторный запуск не создаёт второй таймер. Пауза callbacks при открытом
   редакторе/модальном окне фиксируется отдельно; это не смерть CLO.

Проверка потока консервативная: поток скрипта должен быть единственным потоком,
владеющим видимыми top-level окнами текущего процесса. Если окон нет, потоки
различаются или их несколько, probe отказывается от запуска **до API-вызова**.
Это вспомогательное свидетельство UI-потока, не обещание поддержки API со стороны
CLO. При отказе нужен вывод, а не ручное отключение проверки.

## Длительность и остановка

- Обновлённый запуск ограничен одной минутой по monotonic clock. Один API-вызов
  примерно раз в пять секунд, отчёт примерно раз в 30 секунд, таймер 250 мс.
- По истечении 60 секунд следующий доставленный callback вызывает
  `STOP reason=one_minute_limit`. Пока CLO не обрабатывает сообщения,
  автоматическая остановка также не выполняется.
- Для ручной остановки открыть и выполнить `plugin/clo3d_mcp_probe_stop.py`.
  Ожидается `STOP reason=manual`, `state: stopped`,
  `timer_cleanup_pending: False`. Сам CLO остаётся открытым.
- Повторно выполнить stop-файл спустя несколько секунд: `ticks` и `api_calls`
  должны остаться прежними. `ignored_ticks` может вырасти из-за уже поставленных
  в очередь сообщений Windows: они не вызывают API.
- Если вывод после закрытия редактора недоступен, состояние всё равно хранится
  в памяти: повторный probe/stop печатает его текущую сводку.
- Для проверки автостопа заново открыть обновлённый probe с диска и запустить,
  проверить `auto_stop_seconds=60` в `ARMED`, закрыть редактор, подождать 65–75
  секунд. Затем выполнить **stop-файл**, не probe (probe запустит новое поколение).
  В сводке должны быть `stop_reason: one_minute_limit`, `elapsed_seconds >= 60`,
  `state: stopped`, `timer_cleanup_pending: False`, `error: None`.
  Повторный ручной stop не меняет сохранённые `stop_reason` и `elapsed_seconds`,
  хотя префикс строки показывает текущую команду `STOP reason=manual`.
- Уже запущенное старое поколение сохраняет свой прежний лимит. Перед проверкой
  обновлённого файла его нужно остановить stop-файлом; новый запуск не заменяет
  активный callback и не освобождает удерживаемые ссылки.

Первоначальная проверка повторных запусков — десять ручных циклов:
probe → дождаться `FIRST_API` → stop → повторный stop, проверить счётчики.
В каждом цикле должно быть новое значение `generation`, без ошибок/зависаний.
Эти десять циклов уже выполнены (поколения 3–5, 7–13); повторять их не нужно.

Callbacks удерживаются в `builtins` до закрытия CLO: `KillTimer` не удаляет уже
поставленные `WM_TIMER`. Старое поколение не может выполнять работу нового,
даже при повторном использовании timer ID. Память ограничена 16 поколениями
и 32 последними диагностическими строками на поколение. После лимита нужно
штатно перезапустить CLO; **не удалять** `_clo3d_mcp_p0` вручную.

## Признаки отказа

- `NOT_STARTED`, `FAILED`, `STOP_FAILED`, `error` не `None`;
- `ARMED` есть, но за 10 секунд свободного UI нет `FIRST_API`;
- после закрытия Script Editor счётчики перестали увеличиваться;
- несовпадение native thread IDs, зависание, аварийное закрытие CLO;
- API-счётчики продолжают увеличиваться после успешного stop;
- `timer_cleanup_pending: True` после stop.

При отказе прекратить проверку и прислать вывод. Если UI доступен, выполнить
stop-файл; если stop не подтверждён, штатно закрыть CLO. Не повторять запуск
много раз, не менять флаги legacy listener. Автоматическая остановка не может
прервать зависший синхронный CLO API-вызов.

## Что прислать для приёмки P0

- Версию CLO и начальные строки окружения.
- `FIRST_API`, `ALREADY_RUNNING` после закрытия редактора,
  итоговый отчёт со `stop_reason: one_minute_limit` после минутного автостопа.
- Два последовательных stop-отчёта для сравнения счётчиков.
- Результат десяти циклов и наблюдения об отзывчивости UI/модальных окнах.

До успешной проверки на реальном CLO этапы P1–P3 не начинаем.

## Автоматические проверки (не приёмка CLO)

`tests/test_probe.py` проверяет fake-планировщик, защиту от reentrancy,
stop/restart, повторное использование ID, запоздалые callbacks, ошибки API,
неверный поток, ограничения времени/памяти и отсутствие файлового IPC.
Отдельный тест на Windows запускает настоящий `SetTimer` в изолированном
Python-процессе с собственным message loop и timeout 10 секунд. Он проверяет
ABI/доставку/остановку, но **не использует CLO**. Если Windows недоступен,
этот тест явно пропускается.
